# Concise Solution 1 Oracle design
Oracle IDs must be o1, o2, o3 in output order. Request IDs identify requests; do not use long CVE-based Oracle IDs.
Return {oracle, analysis} matching Schema, descriptions in Chinese. Only use evidence, tp, extraction_analysis. No browsing, execution or data preparation. Explain template choices, sources and missing information in analysis (under 1000 Chinese characters), not in extra output fields. No plans or plan references.
Internally combine joint trigger changes and distinguish alternative locations. Select all distinct supported goals: O1 unauthorized resource operation, O2 illegal capability acquisition AND subsequent use, O3 victim request state/identity contamination. TP alone cannot select templates. Avoid duplicate goals.
subjects maps actor names to plain-language descriptions of identity, permissions and duties. Prefer attacker and victim; reuse victim for observation when authorized. Never add trusted_observer by default. Distinguish victim observer account from target user resource; deleting the observer may prevent later reading. resources describes required objects, symbolic IDs, ownership, scope and initial state in natural language, no methods/paths or preparation steps.
For the cross-world deletion case, victim is the victim-world manager/observer account, target_user is a separate resource. Do not invent ORM pseudocode or SQL from snippets: query must be null unless the exact read mechanism and schema are evidenced. extract contains field paths or null, never expected booleans posing as extracted facts. The mere existence of a deleted filter does not prove soft_delete sets that flag. Unknown post-delete semantics stay unknown. Optional negative controls must use isolated equivalent resources rather than risking the attack target baseline.
permission_checks use real API or trusted database queries for identity, effective permissions, ownership/delegation/sharing and why the operation should be restricted. Reading one's own users proves visibility, NOT delete permission or absence of cross-world authorization. Unknown API/query/extract paths are null, gaps explained in analysis. expected_policy has independent evidence basis.
controls.positive/negative are optional lists, [] if inapplicable. Use authorized operation and applicable denial controls; isolate write effects. A 404 probe does not prove effective permissions or health.
Every API request (attack_request, controls, permission_checks, observations, capability_use_requests and victim_requests) uses the TP request structure plus actor: id, method, handler, endpoint, params:{path,query}, headers, body, response, actor. Preserve evidenced fields from TP, including body.format/body.fields and response.status_code; never flatten body or path parameters into parameters. Keep endpoint placeholders and bind them in params.path. response describes source/documentation expectations, not execution. Unknown fields remain null. Preserve mutation and authentication uncertainty. All actors must be declared in subjects.
resources MUST be a dictionary mapping resource names to natural-language descriptions of ownership, scope and initial state, e.g. attacker_world, victim_world, target_user. Subjects remain in subjects. Consistently use $attacker_world.id and $target_user.id in requests and observations; target_user is a user resource, not its ID value. For cross-world deletion, path world_id binds $attacker_world.id while body user_id binds $target_user.id belonging to victim_world.
Every observation additionally requires actor and target even when api/query are null. target maps identity/scope fields to resource bindings, e.g. {"id":"$target_user.id","world_id":"$victim_world.id"}. Before/after must bind the same target and scope and use the same authorized observer unless evidence requires otherwise. An observation API's actor must match its observation actor. Do not omit these fields when the read channel is unknown. Keep per-observation extract and assertion plus overall success_condition; no invented GET endpoint or SQL.
O2 adds capability_change and capability_use_requests, using beneficiary credentials, never observer credentials. O3 adds victim_requests, shared_state_conditions, schedule with relation/condition/reset/attempt_limit, preserving both identities and dependencies. O1 omits these optional fields.
verifier contains one type, observations, one success_condition string. Type is protected effect: DELETE with GET observations is DELETE. O2 PRIVILEGE_USE; O3 STATE_ISOLATION. Ordinary writes need before/after only; extra stages only when necessary for O2/O3. No redundant status/health/control observations; validity constraints belong in success_condition. Unknown api method/path/query/extract values null, never invented. No runtime verdict or conclusion_rules.
Every observation requires assertion: a concrete check against the values returned by its real API or trusted read-only query. extract identifies response/result field paths; assertion states expected properties, never presents expectations as observed facts. For DELETE, before uses a trusted user's actual read API or trusted SQL to confirm the target exists, belongs to the intended scope, and is initially not deleted. after uses the same trustworthy identity/channel and target binding to verify the version-specific deletion state; account for filtering, permission loss and query failure. Keep api and query as alternative observation channels, selecting one when known. If neither is evidenced, retain null and still describe the required assertion and missing channel in analysis. success_condition combines before/after assertions with authorization prerequisites; it does not replace per-observation assertions.
READ: trusted protected baseline, exclude echo/public/own/default data. CREATE: prior absence and independent actual creation in right scope. UPDATE: same object/field, old!=new, actual=new. DELETE: prior existence and actual deletion semantics, exclude filtering/access loss/query failures. soft_delete() alone does not establish deleted=true or that list disappearance proves deletion; preserve this gap. Success requires identity/authorization, applicable controls, actual effect, target/scope consistency, healthy observation and exclusion of stale/concurrent effects. Status code alone insufficient. O2 proves illegal acquisition and actual capability use; O3 links effect to victim with scheduling baseline. Preserve version uncertainty.
